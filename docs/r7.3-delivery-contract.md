# R7.3 Regression delivery contract

This document is the implementation contract for the P0 items in
`task_now.md`. It keeps the API regression-specific and does not introduce a
universal task framework.

## Public capabilities and schema

- `API_SCHEMA_VERSION` identifies the JSON-facing API independently of the
  package version.
- `capabilities()` returns a JSON-serializable declaration of supported
  regression operations, statuses, artifact formats, and trust boundaries.
- Public result objects retain their typed Python fields for compatibility and
  provide `to_summary()` for a stable JSON-serializable view. The summary does
  not expose VES Core `Evidence` or `VerificationRecord` objects.

## Search lifecycle

`run_regression_search()` creates its search id before candidate execution.
All candidate and final artifacts live under one tree:

```text
runs/<search-id>/
  config.json
  provenance.json
  summary.json
  best_solution.py
  candidates/
    draft0/
      solution.py (or code/solution.py for Docker)
      stdout.log
      stderr.log
      predictions.json (or output/predictions.json for Docker)
      run.json
```

Candidate `run.json` files classify generation/execution, timeout, missing or
invalid artifact, verification failure, and verified evidence. Rejected totals
remain available for compatibility, but callers do not need to infer failure
causes from that total.

## Applying a verified solution

`apply_regression_solution()` applies selected code to a caller-provided full
training set and formal unknown test set. Untrusted/LLM code uses Docker by
default; local execution requires an explicit trusted-code opt-in.

Without official test labels the only successful status is
`produced_unverified`. The result and persisted summary contain no RMSE, MAE,
or other claimed quality metric. They contain prediction/code/data hashes,
logs, artifact paths, runner environment, and Docker image identity.

## Provenance

Search and application runs persist:

- SHA-256 fingerprints for candidate-visible and host-only input files;
- best/applied code SHA-256 and prediction artifact SHA-256;
- VES-Modeling and VES Core package versions and source commits when available;
- generator kind and sanitized provider host/model (never URL credentials,
  headers, tokens, or API keys);
- Docker image reference and resolved/configured digest, timeout, and resource
  configuration;
- caller-supplied JSON split metadata (seed, strategy, grouping/time limits)
  when the data was prepared by an upstream workflow.

## Regression data contract

- `target_column` is explicit and defaults to `target` for compatibility.
- `id_column` is optional. It must be present and unique in train, public test,
  and host labels when configured.
- Train features (excluding target) and test columns must match exactly in name
  and order. Duplicate columns, missing values in IDs, duplicate IDs, and host
  ID mismatches fail before generation or execution.
- Default `row_order="input"` keeps the existing numeric prediction array.
- With an `id_column`, `row_order="id"` requires predictions as
  `[{"id": ..., "prediction": ...}]`; the host aligns them to test IDs and
  rejects missing, duplicate, or extra IDs.
- Split metadata is descriptive provenance, not hidden truth, and must be JSON
  serializable. Host labels remain outside candidate-visible directories.

### Replay environment

`ves replay` reconstructs the host context through environment variables:
`VES_MODELING_HOST_DIR` (required), plus optional
`VES_MODELING_DATASET`, `VES_MODELING_TARGET_COLUMN`,
`VES_MODELING_ID_COLUMN`, and `VES_MODELING_ROW_ORDER`. Whenever an ID column
is configured, `VES_MODELING_PUBLIC_DIR` is also required so replay can
validate public IDs and align host labels. These paths are runtime
configuration and are not persisted in public summaries or provenance.

## Acceptance criteria

1. Existing callers and default array artifacts remain compatible.
2. Search ids exist before execution and every attempted candidate has logs and
   a structured `run.json` under the search tree.
3. Search/application summaries round-trip through `json.dumps()` without
   custom encoders and contain no Core objects, paths, secrets, or hidden labels.
4. Applying untrusted code uses Docker and reports `produced_unverified`; no
   verification metric is present without labels.
5. Provenance hashes change when code/data change and never include raw hidden
   values or credentials.
6. Feature-order, target/id, prediction-ID, and split-metadata errors fail fast
   with regression tests.
7. `ruff check .`, non-Docker tests, and Docker security tests pass.
